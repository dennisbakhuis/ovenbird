# ui

Web UI of ovenbird: Svelte 5 (runes) + TypeScript + Vite, no SvelteKit. Hash routing
(`#/home`, `#/setpoint`, `#/weather`, `#/pump`, `#/settings/<section>`, `#/activity/<tab>`,
`#/system`, `#/system/signals`, `#/system/shadow`, `#/system/trial`, `#/house`, `#/house/model`, `#/house/control`, `#/house/learning`, `#/house/what-if` (its inputs live in the query: `outside`, `comfort`, `sun`, `stove`), `#/more`; the
aliases `#/shadow` and `#/trial` open the System tabs), `base: './'`, and relative API calls (`api/v1/...`)
so it works behind any path prefix such as Home Assistant ingress. The WebSocket URL is derived
from `location`. No CDN assets; system font stack; hand-rolled SVG charts (no chart library).

Architecture: `docs/architecture.md`.

Contract: `docs/api-v1.md`.

## Commands

```fish
npm ci --ignore-scripts
npm run dev        # Vite dev server, proxies /api (incl. WebSocket) to 127.0.0.1:8080
npm run dev:mock   # mock server for every api/v1 endpoint and a fake WS stream (see Mock server)
npm run build      # output in dist/
npm run check      # svelte-check (strict TypeScript)
npm run lint       # eslint + prettier --check
npm run format     # prettier --write
npm test           # vitest (unit + jsdom component tests)
npm run e2e        # Playwright against `vite --mode mock`; BASE_URL=... for another server;
                   # screenshots in e2e/shots/. With BASE_URL the routes spec and the real-service
                   # flows (e2e/real.spec.ts: validate, apply, rollback, pause/resume) run; the
                   # mock-only flows are skipped.
```

Against a running (simulated) service, use the dev proxy; it adds the credentials and rewrites
the `Origin` header so state-changing requests pass the service's origin check:

```fish
env OVENBIRD_PROXY_AUTH=admin:ovenbird-dev npx vite --port 5198 --strictPort --host 127.0.0.1
env BASE_URL=http://127.0.0.1:5198 npx playwright test
```

`mock/fixtures/{config,schema,codes}.json` are copied from
`packages/service/tests/fixtures/ui/` (generated by the backend); do not edit them here.

The mock keeps the configuration (stored values and versions) per scenario cookie; without a
cookie it is shared.

`GET /__frame?route=home` shows the app in an ingress-style iframe (Home Assistant sidebar and
toolbar stand-in). `#/dev-charts` is the chart-kit gallery (mock mode only).

`POST control/stove` starts (with `until`, default 8 h, at most 24 h) or stops wood-stove mode
for the browser's scenario; it answers 409 while `control_stove_enabled` is off.

The mock also answers the wave-3 endpoints: `shadow/divergence`, `trial/status`, `insight/runs`,
`control/snapshot` (GET, and POST to capture one by hand while ovenbird does not control),
`control/release` (GET and POST, per browser; a rehearsal never touches the global pause;
`{"rehearsal": true, "dry": true}` plans without sending), `shadow/episodes/explain`
(per browser), `notifications/status` and `POST notifications/test`, `system/about`,
`diagnostics` (JSON only), `insight/house`, `insight/house/history`, `insight/house/balance`, `insight/house/series`, `insight/house/control` (the model plan: the switch, guards, the latest evaluation and 7 days of computed shifts), `insight/house/whatif` (computed from the house constants of the mock: loss = UA × ΔT, steady-state water temperature, exponential drift),
`GET` and `POST insight/house/run` (a manual run lasts four seconds, kept per scenario cookie) and
`POST insight/house/proposal/draft`. `PUT config/ha` stores the Home Assistant connection
(shared, token write-only) and `POST config/ha/test` answers deterministically: the host
`unreachable.local` cannot be reached, the token `wrong-token` is rejected, anything else
connects. `format=csv` works on `history`, `decisions`, `commands`,
`alarms` and `audit`; the UI's CSV buttons download those, and every chart table can save its
own rows as CSV.

The mock is more forgiving than the service in places (it accepts `weather?back_h=0`, the
service answers 422) and its clock is the browser's; check a change against the simulated
service too before calling it done.

## Review gate

What the v2 gate checked, to repeat after larger changes: `check`, `lint`, `test`, `e2e`; every
route at 1400 px and 400 px, light and dark, on the mock and read-only (GET) on the simulated
service; the framed page; Dutch; keyboard, focus rings, contrast, reduced motion; bundle size;
phone page heights at 400 px against these budgets (Home 1 900,
Setpoint 2 500, Weather 1 600, Commands 2 000, Signals 1 500, Settings Room 1 600, Emitter
1 800; nothing above 2 500). Home and Pump are measured in Dutch as well (`routes.spec.ts`,
"Dutch phone heights").

## Layout

- `src/pages/` one file per route; `pages/settings/` has the Settings sections.
- `src/components/ui/` the shared primitives (next section).
- `src/components/shell/` the app frame: status strip, control line, pump pair, draft bar.
- `src/components/<feature>/` one folder per feature: `activity`, `charts`, `hold`, `home`,
  `house`, `insight`, `pump`, `setpoint`, `settings`, `shadow`, `stove`, `system`, `trial`,
  `weather`, plus `help`, `brand` and `art`.
- `src/lib/core/` API client, types, `LiveStore`, router, formatters, theme, chart maths and
  other code shared by every feature.
- `src/lib/<feature>/` the logic of one feature; `lib/i18n/` typed EN/NL dictionaries, one file
  per page namespace; `lib/help/` the help content.
- `mock/` fixtures, Vite middleware and fake socket; only used with `--mode mock`.
- `e2e/` Playwright specs; screenshots in `e2e/shots/`.

Import aliases (Vite and `tsconfig.json`): `$lib` is `src/lib`, `$components` is
`src/components`, `$ui` is `src/components/ui`. Example: `import Button from '$ui/Button.svelte'`.

Dependencies are pinned to exact versions in `package.json`.

## Primitives

`src/components/ui/` holds every control and container a feature needs. Features compose
these and never write a raw `<button>`, `<input>`, `<select>`, `<textarea>` or `class="card"`.

| Primitive                                   | Use it for                                                                                                                |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `Button`                                    | Every button and button-like link. Variants default, primary, danger, ghost, link, icon; sizes sm and md; `href`; `busy`. |
| `FileButton`                                | A button that opens a file picker.                                                                                        |
| `TextInput`, `Select`, `Checkbox`, `Switch` | The form controls.                                                                                                        |
| `FormRow`                                   | Label, hint and error around one control.                                                                                 |
| `InlineMessage`                             | An error, warning or ok message inside a card or form.                                                                    |
| `Banner`                                    | A page-level notice.                                                                                                      |
| `ActionRow`                                 | A row of buttons, aligned and wrapped consistently.                                                                       |
| `Segmented`                                 | A choice of a few options (pressed or radio semantics; several appearances).                                              |
| `Tabs`, `Stepper`                           | Tabbed sections and step flows.                                                                                           |
| `Card`                                      | Every card: title, subtitle, icon, link, grid span.                                                                       |
| `SectionHeader`                             | A heading with optional subtitle and actions.                                                                             |
| `Pill`, `StatusDot`, `StatChip`             | Status chips, dots and key figures. `Pill` can be interactive.                                                            |
| `Details`, `Why`                            | Collapsible detail and the "why" popover.                                                                                 |
| `EmptyState`                                | A card with nothing to show.                                                                                              |
| `Icon`                                      | The icon set (`lib/core/icons.ts`).                                                                                       |
| `Overlay`                                   | The base of `Modal`, the `Why` popover, the help drawer and the app menu: layer, escape, outside click, focus.            |
| `Modal`                                     | A dialog on top of `Overlay`.                                                                                             |

## Restyling

Change the look from the bottom up:

1. Tokens in `src/app.css`. A colour, radius, size, weight or layer is changed once, here,
   in both the light and the dark theme.
2. The primitive. A new look for all buttons is a change in `Button.svelte`.
3. A feature component only when the change is specific to that feature.

Feature components do not hard-code colours, radii, font weights or z-indexes. They use
tokens.

## Token families

Defined in `src/app.css` for light and dark:

- Brand: `--brand-*`.
- Surfaces and text: `--bg`, `--surface`, `--surface-2`, `--card`, `--border`, `--muted`,
  `--accent`, `--on-accent`, `--on-solid`, `--backdrop`.
- Status: `--status-*`, `--ok`, `--warn-*`, `--err-*`, `--cat-*`.
- Energy labels: `--label-a` to `--label-g`, `--on-label`.
- Charts: `--series-*`, `--chart-*`, `--band-*`, `--wf-*`.
- Scale: `--space-1` to `--space-6`, `--radius-sm`, `--radius-control`, `--radius-pill`,
  `--fs-*`, `--fw-*`, `--lh-*`, `--control-h`, `--card-pad`, `--page-max`.
- Layers and motion: `--z-*`, `--dur-fast`, `--dur-slow`, `--shadow-raised`, `--shadow-pop`.
- Fonts: `--font-display`, `--font-mono`.

Breakpoints are listed in the header comment of `app.css`; JavaScript reads them from
`lib/core/breakpoints.ts`.

## Guard tests

They run in `npm test` (and `make ui-check`).

- `lib/core/theme.test.ts`: every token is defined in both themes; every `var(--x)` used in
  `.svelte` and `.ts` files exists; no colour literal, no literal pill or control radius in a
  `<style>` block; contrast of the palette.
- `lib/core/primitives.test.ts`: no raw controls or cards outside `components/ui/`.
- `lib/core/structure.test.ts`: components and lib modules sit in `ui/`, `shell/`, `core/` or a
  feature folder, never loose. A new folder must be added to the lists in that test.
- `lib/core/mockDrift.test.ts`, `mockShapes.test.ts`, `mockFidelity.test.ts`: the mock server
  follows the API shapes. The service fixtures are copied with `make ui-fixtures`.
